# История экспериментов: путь к текущему решению

Этот файл честно документирует все опробованные подходы — включая провалившиеся —
и обоснование каждого архитектурного решения. Каждая цифра ниже получена на
**полном реальном 20-минутном заезде (221 чанк, 11 271 кадр, непрерывная
последовательность)**, а не на отдельных отобранных кадрах, если не указано иное.

## Tier 1: локальный геометрический детектор препятствий

| Версия | Ложные срабатывания (FPR) | Латентность | Что изменилось |
|---|---|---|---|
| v1 (наивный криволинейный габарит) | 72.3% | 89 мс | Первая версия: глобальная квадратичная парабола для оси пути |
| v2 (интерполяция по якорям) | 53.6% | 121 мс | Замена глобального полинома на `np.interp` по срезам + подавление в зонах низкой достоверности |
| v3 (stateful, EMA-состояние) | 58.9% | 82.5 мс | Персистентное состояние вместо перефита с нуля — задержка исправлена, но FPR ХУЖЕ (залипание состояния) |
| v3 + Fix4/5/6 | 25.33% | ~102 мс | Fix5: исключение контррельса (`guard_rail_limiter`); Fix6: порог минимум 300 точек для доверия дальним срезам |
| hybrid_clearance_solution (регрессия §3.7 исправлена) | 6.21% | ~95-140 мс | + воксельная кластеризация, Tier2 с семантическими правилами, исправленная регрессия на межпутевых опорах |
| **hybrid_clearance_solution (текущая, §3.8)** | **5.52%** (chunks 0-135) | ~95-140 мс | + геометрическая зона исключения края платформы в Tier 1 (`PLATFORM_EDGE_*`), физически откалиброванная по разметке KatLab |

На отдельном validation-баге организаторов (1510 кадров синтетических вставок): **10.8%** флагированных кадров.

### Ключевые уроки, полученные НЕ с первого раза

1. **7 отобранных кадров ≠ честная валидация.** Первая версия криволинейного
   габарита показала 0% FP на 7 вручную отобранных кадрах — полный прогон на
   11 271 кадре показал 72.3%. С тех пор каждая версия проверяется на полном
   датасете, прежде чем цифры публикуются.
2. **Агрегатный процент может скрывать взаимно компенсирующиеся эффекты.**
   При переходе v3→v3+Fix у одних чанков FPR упал до 0% (реальное улучшение),
   у других вырос почти до 100% (новая регрессия) — итоговое среднее осталось
   почти неизменным. Нужно сравнивать по чанкам, а не только общий процент.
3. **Высота не всегда отличает препятствие от инфраструктуры.** Межпутевая
   стена/опора (`pillar_support`) физически занимает ту же высоту (0.2-2.3м),
   что и стоящий/упавший человек — по высоте их не различить. Различает
   ширина: реальный компактный объект (человек, груз) уже ~1.2-1.3м, стена —
   нет.
4. **Самовозвратное искажение (self-referential corruption).** Если геометрия
   пути перефитируется из точек того же кадра, который проверяется на
   препятствие, крупный объект в кадре искажает саму систему координат,
   относительно которой его же ищут. Решение — персистентное состояние,
   обновляемое ТОЛЬКО не-препятственными точками (но это создало собственную
   проблему №2 из списка ниже).
5. **Исключение "подозрительных" точек из обновления состояния может
   зациклиться.** Если слайс один раз получил смещённую оценку, а точки,
   которые могли бы его исправить, продолжают классифицироваться как
   "препятствие" и исключаться — слайс остаётся неверным сколь угодно долго.
   Нужно принудительное периодическое обновление по ВСЕМ точкам без
   исключений.

## Tier 2: почему не нейросеть, а one-class модель на ручных признаках

Обучающих данных с реальными препятствиями катастрофически мало: во всём
20-минутном реальном заезде нет ни одного подтверждённого случая постороннего
предмета на пути (что хорошо для безопасности метро и плохо для supervised
обучения). Два независимых нейросетевых подхода были опробованы и оба
провалились по одной и той же причине:

* **Классификатор (PointNet)**, обучаемый отличать реальные фоновые кластеры от
  СИНТЕТИЧЕСКИХ препятствий — достигал ~100% точности уже за 5-10 эпох на
  любой генерации синтетики, сколько бы её ни улучшали (устранение дублей
  точек, реалистичная intensity, стратификация по planarity). Модель училась
  находить артефакты генератора синтетики, а не геометрию препятствия.
* **Автоэнкодер** с той же обучающей выборкой негативов показал обратный
  эффект: синтетические формы реконструировались ЛЕГЧЕ (ошибка 0.135), чем
  настоящий шумный фон тоннеля (0.198-0.209) — противоположность нужному
  сигналу для аномалий.

Вывод: дело не в конкретной архитектуре — любой достаточно гибкий метод
находит статистическую разницу между синтетикой и реальностью вместо
семантики "препятствие против нормы". Поэтому принята **one-class модель
Махаланобиса**, обученная ИСКЛЮЧИТЕЛЬНО на реальных фоновых кластерах;
синтетика используется только для последующей проверки, никогда для
обучения. Результат на честном train/val/**test** сплите по времени
(6817/2153/2095): **2.8% FPR / 100% TPR** на отложенном test (согласуется с
2.6% на val — не переобучились).

## Что ещё не решено (открытые ограничения)

* Честный FPR — 5.52% на чанках 0-135 основного датасета, не 0%. Остаточные
  срабатывания сконцентрированы в ранее известных сложных зонах
  (широкие/станционные участки), уровень которых сопоставим с фоновым шумом
  остального датасета.
* Пороги нового правила `pillar_support` (ширина ≥1.3м / протяжённость
  ≥1.8м) и геометрической зоны `PLATFORM_EDGE_*` (§3.8 README)
  проверены только на этом маршруте — при развёртывании на другой линии
  метро рекомендуется повторная калибровка на её реальных данных.
* **Найдено и НЕ исправлено (осознанно):** на validation-баге организаторов
  приближающееся синтетическое препятствие (кадры 463-479) периодически
  "мерцает" — классифицируется то как `hazard`, то как `station_platform_edge`
  Tier2-правилом, из-за того что граница по сферичности кластера
  (`sph <= 0.06`) оказалась на уровне шума точек у этого конкретного объекта.
  Объект в итоге стабильно детектируется на более близкой дистанции (с кадра
  474), TPR не теряется полностью, но первое появление иногда пропускается.
  Попытка поднять порог `mean_dx` правила с 0.75 до 1.35м устранила мерцание,
  но честная проверка на чанках 103-134 основного датасета показала рост FPR
  11.8%→15.5% — реальные откат отменён (см. §3.8 README): FPR на реальных
  данных важнее устранения мерцания на синтетике.
* TPR (100% на юнит-сценариях) измерен на синтетических вставках — реальных
  случаев препятствия на пути в имеющихся данных нет и по счастью не было,
  так что честная TPR-оценка на подлинных инцидентах невозможна без
  дополнительных полевых данных.
